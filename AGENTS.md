# AGENTS.md — Project guide for AI agents and maintainers

This document describes the **mind** project: its architecture, behavior, technical choices, and how to use it. It is intended for AI agents and human maintainers. **Agents that modify this codebase must keep this file updated** when they change architecture, add commands, change config, or alter behavior (see [Keeping this document updated](#keeping-this-document-updated)).

---

## 1. Project overview

**mind** is a CLI tool for persistent long-term memory — tracking thoughts, ideas, tasks, and knowledge. Data is organized into named **spaces**, each containing **memories** with full-text search, tags, links, and a 3-tier CPU-cache-style access-frequency system.

- **Runtime:** [Bun](https://bun.sh/)
- **Language:** TypeScript (strict mode, ESNext)
- **Entry point:** the **`mind`** Bash script at project root; invokes `src/mind.ts`. Supports subcommands: `serve` (HTTP server), `mcp` (MCP server), `setup` (agent configuration), and `update` (self-update from GitHub releases). Also supports `--complete` flag to delegate to `src/complete.ts` (not yet implemented).
- **Persistence:** SQLite database at `data/mind.db` (path configurable via `MIND_DATA_DIR` env var or `MIND_DB_PATH` for full path override). The legacy `brain.json` is supported as a migration source via `mind import`.
- **RAG/Embeddings:** Optional semantic search with a selectable embedding provider (`MIND_EMBEDDING_PROVIDER`: `openai` default or `openrouter`; invalid values disable RAG without fallback). Enable with `MIND_RAG=true` + `OPENAI_API_KEY` (OpenAI) or `OPENROUTER_API_KEY` (OpenRouter). The model stays `text-embedding-3-small` (`openai/text-embedding-3-small` on OpenRouter) at 1536 dimensions, so stored vectors remain compatible without re-embedding. Embeddings are stored as BLOBs in SQLite and generated with an awaited request on add/update/move/patch (not fire-and-forget).
- **Search pipeline:** One unified relevance pipeline backs CLI `search`, MCP `memory_query(search)`, and `GET /api/search`. A parser turns input into an AST (quoted `"phrases"`, `OR`, `AND` = implicit AND, `NOT`, trailing `*`; malformed input degrades to a literal AND and never errors) and logically independent channels collect candidates: lexical rungs (phrase → all → any), trigram substring, fuzzy (Damerau–Levenshtein ≤2, capped expansions), LIKE for sub-trigram terms, token-set coverage, and the optional semantic channel. The channels execute sequentially on one synchronous SQLite connection, so “fan-out” describes the candidate model, not concurrent execution. A per-query weighted fusion (with an agreement bonus) ranks results deterministically and attaches a per-result `confidence` bucket (`high`/`medium`/`low`) plus `methods` provenance. Semantic admission is independent of the lexical gate: natural-language queries (one group, no `NOT`, only terms) admit semantic candidates at cosine ≥0.6 even when lexical results exist, while explicit phrases, prefixes, and operators stay lexical. With RAG off the semantic channel is omitted silently; a query-time embedding failure opens a ~5-minute in-memory breaker so a failing provider cannot trigger retry storms.
- **Layout:** **`src/`** contains CLI, MCP, and API server code. **`test/`** contains backend/CLI tests. **`web/`** contains frontend source (`web/src`), styles (`web/styles`), static assets (`web/assets`), static HTML shell (`web/public`), and web-specific tests (`web/test`). **`scripts/`** contains E2E and evaluation scripts (including `scripts/search-eval.ts`, the relevance-suite runner).
- **Cognitive lifecycle docs:** The [documentation index](docs/README.md) groups all living pages. [`docs/cognitive-memory-lifecycle.md`](docs/cognitive-memory-lifecycle.md) explains the memory model, tiers, lifecycle, writing, supersession, linking, living references, and tool usage; [`docs/skill-first-distribution.md`](docs/skill-first-distribution.md) explains the skill-first activation and installation model; [`docs/agent-integration-matrix.md`](docs/agent-integration-matrix.md) records per-client paths and validation status; and [`docs/search-engine.md`](docs/search-engine.md) describes current retrieval behavior. Exceptional historical evidence lives under [`docs/history/`](docs/history/); execution, merge, and validation reports stay in `.pas/`, and no report is added to the docs root. The normative agent instructions remain the canonical protocol in `src/resources/protocols/mind-cognitive-protocol.md`.
- **Neural Map MVP:** web SPA includes a read-only per-space graph view using a minimal graph API payload and on-demand memory detail fetch, with adaptive multi-lane radial placement, dense-map culling (no persistent labels; one transient label on hover/focus/selection, bounded edges, in-circle degree numbers, zero overlaps), dragging that never selects graph text (the accessible table stays selectable), and higher zoom ceiling for dense maps.
- **Web SPA URL routing:** client-side URL contract is `/` (All spaces), `/spaces/{encodedSpace}?view=list|map&memory=&q=&tag=&tier=&tiers=1,3&confidence=&semantic` (space detail with in-space search), and `/logs`, with reload restore, browser back/forward support (`popstate`), and safe fallback canonicalization when route params are invalid. All spaces is the first sidebar entry (a real anchor to `/` with `aria-current` only on home) and the topbar has no breadcrumb. All spaces has a compact, client-only search over loaded visible spaces (name, description and tags; case- and accent-insensitive AND tokens) that never changes the URL or calls the memory API and keeps its query across space navigation; it has no space/memory/embeddings summary, and the sidebar storage row always uses the global status. Search lives inside the open space via the header search input (`/` focuses it); there is no global search route, and `/search` canonicalizes to `/` (or the current space). A query or `confidence` filter opens the space-search view; `tier`/`tiers`/`tag` alone stay list filters.

## 2. Architecture

### 2.1 High-level flow

```
User → ./mind <command> [args] [--flag value]
         ↓
    mind (Bash script at repo root)
         ↓
    bun run src/mind.ts "$@"
         ↓
    executeCommand(args, store, logger)
         ↓
    CLI command registry (atomic command modules) → command-executor (dispatch)
         ↓
    MindStore (SQLite) + Logger (stdout/stderr)
```

- **Entry:** `src/mind.ts` creates store/logger and delegates all command handling to `executeCommand` from `src/cli/command-executor.ts`.
- **Commands:** Declared as atomic modules in `src/cli/commands/*.ts` and registered by `src/cli/commands/index.ts`. `src/cli/command-executor.ts` acts as dispatcher/registry.
- **Storage:** All persistent data goes through the `MindStore` interface (defined in `src/store/mind-store.ts`), implemented by `createSqliteStore` (`src/store/sqlite-store.ts`). Uses bun's native `bun:sqlite`.
- **FTS:** Full-text search uses SQLite's FTS5 with a porter tokenizer. FTS is synced **manually** (bun:sqlite has a bug with content-sync triggers — see [§ 3](#3-technical-considerations)).
- **Output:** All user-facing messages go through the `Logger` interface (`src/helpers/logger.ts`), so tests can swap in a mock logger.
- **Web/API:** The single canonical HTTP server is `src/api/server.ts` (via `mind serve`), and it serves API routes plus static web files from the `web/` tree.

### 2.3 Data model

- **Brain:** A SQLite database (`mind.db`) at `data/` in the repo root (or `MIND_DATA_DIR`).
- **Space:** `{ id: string (UUID), name: string, description: string, hidden: boolean, tags: string[], created_at, updated_at }`. Identified by name (unique); UUID primary key for internal references.
- **Hidden spaces:** Spaces can be marked hidden and are omitted from default `list`; include them with `list --hidden`.
- **Checkpoints:** Session checkpoints are stored as tagged memories (`checkpoint` tag) in the same project space.
- **Memory:** `{ id: string (UUID), space_name: string, name: string, content: string, tier: 1|2|3, pinned: boolean, access_count: number, last_accessed_at: string|null, tags: string[], embedding: Float32Array|null, created_at, updated_at, changed_at }`. UUID primary identity; `fts_id` (number) is the SQLite FTS5 surrogate. Identified by `(space_name, name)`.
- **Tier system:**
  - 🔴 **T1 (hot)** — frequently accessed (limit: 25/space)
  - 🟡 **T2 (warm)** — default for new memories (limit: 50/space)
  - 🔵 **T3 (cold)** — rarely used (unlimited capacity)
  - Auto-promotion on CLI `read`: each read promotes one tier up (T3→T2, T2→T1). Skipped silently if pinned or if destination is full and all are pinned.
  - **LRU eviction:** when a tier is full, the least-recently-used non-pinned memory is demoted one tier down (no cascading). T3 is unlimited, so no eviction from T3. If all memories in a tier are pinned, `addMemory` and `promote` throw an error; `recordAccess` promotion silently skips.
  - New memories can be added to T1, T2, or T3 only.
  - **Pinned memories are immune to auto-promotion and LRU eviction.**
- **Link:** Directional edge between two memories with a label (default: `"related"`). Stored as `(source_id TEXT, target_id TEXT, label)` (UUID foreign keys).
- **Tags:** Both spaces and memories can have multiple string tags. Tags are normalized on input: converted to lowercase, leading `#` stripped, validated against allowed characters (`a-z`, `0-9`, `-`, `_`, `.`, `:`, `/`, `=`, `+`, `@`). Tags cannot be empty or contain spaces. Displayed with `#` prefix in CLI output.
- **FTS:** `memories_fts` (FTS5, `porter unicode61`) and `memories_fts_trigram` (FTS5, `trigram remove_diacritics 1`, contentless, schema v10) are standalone virtual tables synced manually on add/update/delete. `memories_fts` powers token/fuzzy matching via the porter tokenizer; `memories_fts_trigram` powers substring matching for terms of 3+ characters and folds diacritics so accented and unaccented queries match both ways (R1).
- **Search pipeline:** Search is one unified multi-channel pipeline (`SearchRepository.searchMemories`) used by the CLI, MCP, and API. A parser builds a query AST (`"phrases"`, `OR`, `AND`, `NOT`, trailing `*`); logically independent channels collect candidates (phrase/all/any rungs, trigram substring, fuzzy Damerau–Levenshtein ≤2, LIKE for sub-trigram terms, token-set coverage, and semantic when RAG is enabled) and execute sequentially on one synchronous SQLite connection; candidates pass a coverage-based admission gate; and a weighted fusion with an agreement bonus ranks them deterministically. Semantic-only candidates from natural-language queries can bypass the lexical gate at cosine ≥0.6; explicit operators remain lexical. Each result carries a normalized `score`, a `confidence` bucket (`high|medium|low`), and `methods` provenance. RAG-off search stays fully functional (the semantic channel is omitted); a query-time embedding failure opens a ~5-minute in-memory breaker. The embedding provider is selectable (`openai` default or `openrouter`) without changing the ranking math; both providers produce 1536-dimension vectors, so stored embeddings stay compatible.

## 3. Technical considerations

- **Schema version:** Current schema is version 10. Existing v1 databases (tier `CHECK (tier BETWEEN 1 AND 3)`) are migrated automatically via a 12-step rename-and-recreate pattern in `MIGRATE_V1_TO_V2`. V2→V3 adds the `embedding BLOB` column. V3→V4 adds `changed_at` and backfills it from `updated_at`. V4→V5 adds `spaces.hidden` with default `0`. V5→V6 adds the `logs` table for operation auditing. V6→V7 removes T4 (frozen) tier; all T4 memories migrate to T3 which becomes unlimited. V7→V8 converts `spaces` and `memories` from INTEGER AUTOINCREMENT to UUID TEXT primary keys, adds `memories.fts_id` (INTEGER) as local surrogate for SQLite FTS5 rowid, adds `memories.space_id` (TEXT FK) normalizing the relationship to `spaces`, adds `spaces.id` (TEXT PK), adds the `fts_id_sequence` table for transactional ID assignment. V8→V9 adds the standalone `memories_fts_trigram` FTS5 table (tokenize `trigram`) repopulated from `memories`. V9→V10 (**final consolidated schema**) recreates `memories_fts_trigram` in place with `remove_diacritics 1` + `content=''` + `contentless_delete=1` (R1 + size) and repopulates it. The intermediate schemas v10 (with a per-document search-term dictionary) and v11 (dictionary retired) were **development-only and never published**; the final v10 is functionally identical to that dev v11 and has no dictionary. There is no permanent `v10→v11` compatibility in the engine: dev databases still stamped version 11 are normalized to 10 with the opt-in `scripts/normalize-dev-db.ts` (copies only; refuses `data/mind.db`). Every step runs under the migration-safety wrapper.
- **Migration safety:** Store initialization detects existing DB schema version before migration. If the DB exists and is outdated, mind creates an automatic `*.migration-backup.*.db` backup with SQLite `VACUUM INTO`, runs migrations, validates the final schema version, `PRAGMA quick_check`, and `PRAGMA foreign_key_check`, and restores the backup if migration or validation fails. Fresh/current DBs skip migration backups, and automatic migration backups are pruned to the latest 3 per DB path.
- **Trigram index cost:** `memories_fts_trigram` (contentless, schema v10+) on the real corpus is about **19.9 MB** after the contentless change — roughly 24 % smaller than the old non-contentless trigram (`26.18 MB → ≈19.9 MB`; `−6.27 MB`). On the synthetic scalability corpus at 50k the contentless index measures **111.70 MB vs 149.44 MB** for the old engine (`−25.3 %`), and the compact DB drops from 268.37 MB to 230.63 MB (`−14.1 %`). These are host-specific measurements from the pre-optimization comparison; see [`docs/search-engine.md`](docs/search-engine.md) for the current envelope and [`docs/search-benchmarks.md`](docs/search-benchmarks.md) for reproduction.
- **Semantic breaker:** A query-time embedding failure (for example an expired key) opens an in-memory breaker with a ~5-minute TTL (`SEMANTIC_BREAKER_TTL_MS` in `src/helpers/rag.ts`). While open, the semantic channel is skipped entirely so a failing provider cannot trigger a retry storm; lexical search is unaffected.
- **Bun and lockfile:** The project runs and tests with Bun. Use `bun run`, `bun test`, and Bun's built-in TypeScript + SQLite support. No separate compile step. `bun.lock` is the only root lockfile; `package-lock.json` was removed and the release script has no npm-lock handling. The benchmark subproject owns `benchmarks/agent-memory/bun.lock`.
- **CI:** `.github/workflows/main.yml` pins Bun 1.3.14 and, after a frozen install, runs `bun audit --audit-level=high`, `bun run typecheck`, `bun run format:check`, `bun run lint`, and `bun test test/ web/test`. The benchmark job runs its own frozen install plus the blocking high-severity audit, typecheck, `bun test test`, and `bun test experiments`. No paid stage runs in CI, and audit failures are never suppressed with `|| true` or `continue-on-error`. As of 2026-10-20 the root audit reports zero advisories and the benchmark audit passes at high severity with residual moderate and low advisories that have no upstream fix. CI triggers on every push (including branch names with `/`), every pull request, and manual dispatch. Hosted run evidence for a feature commit is recorded in its `.pas/` feature report; do not claim a green run until it is observed.
- **Checkpoint completion atomicity:** `MindStore.completeCheckpoint` creates the T3 `session-*` summary, copies inbound and outbound links with labels and directions, and deletes the checkpoint in one synchronous SQLite transaction. A summary, link, or delete failure rolls back the entire transformation, leaving the checkpoint and original links intact, so a retry cannot duplicate the summary. Embedding generation runs after the commit and auto-export runs once. `checkpoint-done.ts` only builds content and calls the store; MCP and CLI surfaces are unchanged.
- **bun:sqlite FTS5 bug:** bun:sqlite (v1.2.10) cannot handle FTS5 `content=table` sync triggers — any UPDATE or DELETE on the source table errors with "N values for M columns". **Workaround:** `memories_fts` and `memories_fts_trigram` are standalone FTS5 tables (no `content=` option, no triggers). Both are synced manually through the `FtsHelper` class in `src/store/shared/fts-helpers.ts` (`insert`/`update`/`delete`, mirrored across both indexes) from `addMemory`, `updateMemory`, `deleteMemory`, `deleteMemoryByName`, `deleteSpace`, and `importFromJson`. Because the trigram index is contentless (`content=''`), FTS5's `'rebuild'` is unsupported; recovery uses `delete-all` + repopulate (`recoverTrigramIndex`).
- **Fuzzy channel (P-A, schema v10):** the fuzzy recall channel generates candidates from the **full folded document vocabulary**, folded once and cached in memory per store and keyed by the store write generation (`storeGeneration`/`bumpStoreGeneration` in `src/store/shared/matching-tokenizer.ts`, bumped by every `FtsHelper` write). A steady-state search pays no SQL round-trip for candidate generation; a write can never leave a stale vocabulary behind. Expansions use `bandedOsa` (OSA ≤2 with a hard cap and early exit), a length band, a deterministic sorted order, and the documented **prefix-3 rule** (`FUZZY_PREFIX_LENGTH = 3`): a typo in the first three characters of a word is **not** recoverable. The per-document `search_terms`/`memory_terms` dictionary was a **development-only prototype** (never published) whose storage/rebuild cost did not pay off at 50k; the final v10 does not include it.
- **Styling:** Terminal output uses `ansi-styles` for bold, colors, etc. Tests assert on the styled strings.
- **Config / storage path:** `src/config.ts` resolves `CONFIG.dbPath` from `MIND_DB_PATH` env var (full path override) or `MIND_DATA_DIR` env var + `mind.db` (defaults to `data/` at repo root). The web server uses `MIND_DATA_DIR` (or `/data` in Docker). `data/` is in `.gitignore`. HTTP idle timeouts are configurable via `MIND_MCP_IDLE_TIMEOUT` (default 120s) and `MIND_API_IDLE_TIMEOUT` (default 30s). Log retention is configurable via `MIND_LOG_RETENTION_MINUTES` (default 10080 minutes = 7 days). Web server port is controlled via `MIND_PORT` (default: 30303). RAG is disabled by default; enable it with `MIND_RAG=true`. `MIND_EMBEDDING_PROVIDER` selects the embedding provider (`openai` default or `openrouter`; invalid values disable RAG without fallback), and the per-provider API keys are `OPENAI_API_KEY` (OpenAI) and `OPENROUTER_API_KEY` (OpenRouter).

The contract is: existing files are parsed strictly, and a parse failure aborts the entire setup run with a clear error rather than overwriting the file with an empty default. Content-changing writes are preceded by a timestamped sibling backup (`<file>.bak.YYYYMMDDTHHMMSSmmmZ`) holding the pre-write bytes, and the new content is staged in a sibling `.tmp` file and renamed into place so a crash mid-write cannot leave a partial file. Backups are intentionally not pruned by setup — users can manage them by hand. ### 4.10 Mind source of truth and memory protocol

The `mind-management` skill is the single source of truth for Mind. Load it
unconditionally at session start and after compaction, before any Mind use; do
not call a Mind MCP tool until it is loaded. AGENTS.md, MCP
`initialize.instructions`, tool descriptions, and these docs are activation
pointers only. If the skill is not listed or cannot be loaded, call
`system_instructions` and follow it.

When using mind via MCP, follow these conventions:

The full cognitive model is explained in [`docs/cognitive-memory-lifecycle.md`](docs/cognitive-memory-lifecycle.md), and current retrieval behavior is in [`docs/search-engine.md`](docs/search-engine.md). The canonical six-responsibility protocol is `src/resources/protocols/mind-cognitive-protocol.md`.

**Tags with prefixes:**

- `type:project` — project space
- `type:user` — user preferences
- `type:config` — global configuration
- `type:learning` — learned knowledge
- `type:session` — session summaries
- `cat:decision` — architectural decision
- `cat:bugfix` — bug fix
- `cat:pattern` — established pattern
- `cat:discovery` — technical discovery
- `cat:preference` — user preference
- `cat:config` — configuration
- `status:*` — convention-only lifecycle tags, such as `status:proposed`, `status:validated`, `status:failed`, `status:superseded`, `status:obsolete`, `status:final`, and `status:living`
- `type:reference` + exactly one `ref:*` + `status:living` — living reference memory tags

**Space hierarchy (use repo name):**

> For software projects, use the repository/directory name as the space name (e.g., `projects/mind`, `projects/arcana-web`). This makes memories discoverable by future agents.

- `projects/<name>` — one space per project
- same-space session summaries live inside `projects/<name>` as `session-*` memories tagged `type:session` + `cat:summary` at T3
- `user/preferences` — global user preferences
- `user/patterns` — user patterns
- `global/config` — cross-project config

**Tier usage:**

- T1 (hot) — critical active info
- T2 (warm) — default for new memories
- T3 (cold) — unlimited

**Memory quality guidance:**

- Checkpoints are live/ephemeral work state.
- Session summaries are chronological recovery logs and evidence, not canonical truth.
- Durable/canonical memories are atomic actionable knowledge for future sessions.
- Living reference memories are maintained current-truth maps for project, architecture, style, domain, or workflow context.
- Create durable memories for stable decisions, verified root causes, final fixes, reusable patterns, user preferences, and significant config/domain facts.
- Avoid durable memories for transient observations, routine progress, or routine validation results with no new findings.

**Living reference convention:** use T2 by default, allow natural promotion to T1, and pin only 1–3 critical references when explicitly warranted or approved. Tags are authoritative: use `type:reference`, exactly one `ref:*` category tag, and `status:living`. Recommended refs are `ref:project-map`, `ref:architecture`, `ref:domain`, `ref:workflow`, `ref:style`, `ref:key-decisions`, and `ref:known-pitfalls`; the memory name is a readable stable kebab-case identifier such as `architecture-overview`, `project-map`, `style-guide`, `domain-model`, `workflow-notes`, `key-decisions`, or `known-pitfalls`. Include Purpose, Current truth, Key areas/files/concepts, Active conventions, Source memories, Last reviewed, and Maintenance notes. Update living references with `memory_update` when current truth changes.

**Deletion guidance:** delete only memories that are clearly obsolete, no longer applicable, and have no historical value. Otherwise, mark `status:obsolete` or `status:superseded` and link the replacement.

**Continuity rule:** link directly relevant memories for recovery continuity. `memory_add` with `links_to` is best-effort — check `links_failed` in the response.

### 4.11 Autosync (Experimental)

Mind can synchronize project spaces with `.md` files on the filesystem. The config is stored in `.mind/config.yml` and is versioned with git. Enabled spaces export automatically after successful CLI, API/web, or MCP DB mutations; export failures and conflicts are logged without reverting the primary DB operation.

**Initialize sync:**

```bash
mind sync init
```

**Enable a space:**

```bash
mind sync enable --space projects/mind
```

**Directory structure:**

```
.mind/
├── config.yml           # spaces config (VERSIONADO)
├── .gitignore
└── spaces/
    ├── a1b2c3d4/        # hash of "projects/mind"
    │   ├── manifest.json
    │   └── memory-1.md
    └── ...
```

**Commands:**
| Command | Description |
|---------|-------------|
| `mind sync init` | Initialize .mind/ directory |
| `mind sync status` | Show configured spaces and drift summary |
| `mind sync enable --space <name>` | Enable sync for a space |
| `mind sync disable --space <name>` | Disable sync |
| `mind sync now --space <name>` | Immediate sync |
| `mind sync export --space <name>` | Export to files |
| `mind sync import --space <name>` | Import from files |
| `mind sync conflict --space <name> --strategy <strategy>` | Set conflict strategy |
| `mind sync remove --space <name>` | Remove from sync |
| `mind sync config` | Show config |
| `mind sync serve --space <name>` | Start file watcher |

**Conflict resolution strategies:**

- `db-wins` — DB version wins on real conflicts; only manifest-managed stale files are pruned.
- `file-wins` — file version wins on real conflicts; automatic DB→FS export skips conflicting files and logs a warning.
- `latest-wins` — hashes detect dirty sides first, then normalized UTC timestamps choose a winner. Near-future timestamps within 5 minutes are accepted for clock skew; farther future or invalid timestamps produce conservative warnings/skips.

**Manifest v2 and conflicts:** manifest entries track memory name, managed path, optional DB ID, canonical content and metadata hashes, normalized UTC timestamps, last file mtime, and last sync time. Hashes decide dirty state against the common baseline; file existence alone is not a conflict. Timestamps are for audit, ordering, and `latest-wins` tie-breaking only. `mind sync status --space <name>` reports DB/file/manifest counts, dirty DB and file counts, conflicts, tombstones, missing managed files, and the latest auto-export warning or error when available.

**MCP integration:** When MCP server starts, it auto-starts watchers for all enabled spaces.

**config.yml format:**

```yaml
# mind autosync config

version: 1

# Spaces to sync with this project
# To enable a new space, add it below with enabled: true
# Valid conflictResolution values: db-wins, file-wins, latest-wins
spaces:
  # projects/mind:
  #   enabled: true
  #   conflictResolution: db-wins
```

**Limitations:**

- File deletion does not auto-delete from DB during watcher imports; missing managed files are reported as warning/drift by `sync status` without modifying the DB.
- Existing-memory imports update supported metadata when file-to-DB wins: content, tags, tier, pinned state, and best-effort `links_to`. Frontmatter names do not rename existing memories in this phase.

## 6. Documentation philosophy and maintenance

Documentation is part of the product. Treat it as a current map of the code, not
as a record of every iteration.

### Source of truth and status vocabulary

The code and tests are the source of truth for behavior. Documentation explains
and points to them; it never overrides them. Use this vocabulary consistently:

- **Living** — describes current behavior and is maintained with the code.
- **Historical** — frozen evidence from a past feature. It is not current truth.
- **Session** — work-in-progress state or a task report; it belongs in `.pas/`.
- **Unverified** — implemented or documented, but not confirmed by a live run.
- **Not run** — prepared but not executed, especially for paid benchmark stages.

Never present a historical report or an unrun check as current behavior. Date
external claims and validation statements so readers can judge freshness. The
canonical agent protocol is `src/resources/protocols/mind-cognitive-protocol.md`;
living pages explain it but do not replace it.

### Living versus temporal documentation

- Living pages live in `docs/` and are indexed by [`docs/README.md`](docs/README.md).
  They are the default place to explain current behavior.
- Execution, merge, validation, and test reports belong in `.pas/` and are not a
  permanent documentation surface. No feature is required to produce a permanent
  report, and a completed feature does not need a page in `docs/`.
- `docs/history/` is **not an automatic archive**. Retain a historical report
  there only when it has durable technical value, such as measured experiments,
  rejected alternatives, or open research questions that a living page does not
  reproduce. Every retained report is listed explicitly in `docs/README.md` and
  keeps a two-line frozen banner naming the feature, the freeze date, and the
  living page that supersedes it.
- Release notes live in `docs/release-notes/` and are immutable; never move or
  rewrite them.

### Documentation locations

| Content                       | Location                            |
| ----------------------------- | ----------------------------------- |
| Documentation index           | `docs/README.md`                    |
| Living behavior and concepts  | `docs/*.md`                         |
| Exceptional retained evidence | `docs/history/<feature>/*.md`       |
| Release history               | `docs/release-notes/*.md`           |
| User-facing install and usage | `README.md`                         |
| Contributor and agent policy  | `AGENTS.md`                         |
| Change log                    | `CHANGELOG.md`                      |
| Benchmark methodology         | `benchmarks/agent-memory/README.md` |
| Generated benchmark report    | `benchmarks/agent-memory/REPORT.md` |

### Update before you create

Prefer updating the living page that already owns a topic. Create a new living
page only when the topic has a distinct audience or a clearly separate job that
would overload the existing page. Do not duplicate the same behavior across a
living page, `README.md`, and `AGENTS.md`; link to the canonical page instead.

### Index and link maintenance

- Every living page must be linked from `docs/README.md`.
- Relative links must resolve, including links into `docs/history/`, `src/`,
  `test/`, and `benchmarks/`.
- When you move or rename a page, update its inbound links in the same task.
- When you change a heading that is linked elsewhere, update the anchor.
- `test/docs-links.spec.ts` enforces the invariants rather than a fixed list: the
  living index, retained-evidence links, frozen banners, non-empty Markdown,
  relative links, release notes, and the absence of temporal reports in the docs
  root. Do not add a filename to the test to make a report permanent.

### Documentation update matrix

| Change                                  | Update                                                                    |
| --------------------------------------- | ------------------------------------------------------------------------- |
| User-facing behavior or setup           | `README.md` and the owning living page                                    |
| Architecture, commands, schema, config  | `AGENTS.md`                                                               |
| Search behavior, limits, or performance | `docs/search-engine.md` and `docs/search-benchmarks.md`                   |
| Agent setup or capability status        | `docs/skill-first-distribution.md` and `docs/agent-integration-matrix.md` |
| Verification process                    | `docs/verification-harness.md`                                            |
| Non-trivial or user-visible change      | `CHANGELOG.md` under `## [Unreleased]`                                    |
| Benchmark report format or links        | `benchmarks/agent-memory/src/report.ts` and `REPORT.md`                   |

### Historical evidence and benchmark reproducibility

Keep reproducible scripts and fixtures in the repository. Keep raw or host-local
artifacts external or under `/tmp`, and record only aggregate evidence. Historical
reports keep their original claims and measurements; do not rewrite them when
behavior changes. Instead, add or update the living page and point the historical
banner at it. There is no fixed list of retained reports: the docs test discovers
what remains under `docs/history/` and checks that it is indexed. Treat
host-specific benchmark numbers as context, not contracts; document the method
and ratios, and regenerate before quoting absolutes.

### Review checklist

- [ ] A page moved? History banner, index, and inbound links are updated.
- [ ] New page? It is linked from `docs/README.md` and has a single clear job.
- [ ] A report? It is in `.pas/` unless it has durable technical value.
- [ ] Claims dated or qualified where the evidence is external or unverified.
- [ ] No temporal report added to the `docs/` root.
- [ ] `bun test test/docs-links.spec.ts` passes.
- [ ] `CHANGELOG.md` and `README.md` reflect user-visible changes.
